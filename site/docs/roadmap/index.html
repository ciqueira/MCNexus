Nexus Roadmap

Last updated: November 17, 2026

This roadmap separates implemented capabilities, current work, planned work, and items under consideration. Known limitations and remaining validation requirements are included with the related work. The roadmap does not assign speculative delivery dates.

How to Read This Roadmap

  • A checked item means the capability is implemented in the current code and operating model. It does not by itself claim an SLA, independent security certification, universal host compatibility, or automatic legal compliance.
  • An unchecked item is not yet available as a complete capability. Its scope may change as testing, production evidence, and developer feedback are collected.
  • The Microsoft Store is the official and recommended Windows channel. The direct Windows installer is not currently code-signed, and the macOS build is not yet signed with Apple Developer ID or notarized.
  • Developer integrations are currently reviewed and configured per project. There is no public onboarding API or fully self-service developer portal.
  • The licensing core is not specific to OFX. OFX plugins for post-production hosts are the kind of software served today; other kinds are planned work, listed below.
  • Commerce capabilities are implemented. Broader promotion remains gated by expanded end-to-end operational testing and the applicable legal and accounting review.
  • Each provider layer (identity, payment, licensing, fulfillment, email, and release source) is separated by an explicit contract. What is connected today, and what is on the roadmap for each layer, is listed in Developers.
  • Internal multi-tenancy is not presented as a public SaaS offering. External organizations, membership and RBAC, public onboarding, tenant-scoped service billing, and contractual SaaS operations remain future work.

Product Scope

Nexus manages licensing, release delivery, installation, updates, and rollback for native software that has to keep working without a network connection. It receives a license, purchase, or authorized grant, resolves the applicable entitlement and release, and makes the artifact available to the client.

The platform is organized in two layers, and they advance independently.

  • Licensing core (host-independent): Activation certificates signed per tenant, machine binding, entitlements, seat control, an offline validity window, synchronization policy, and an audit trail. An activation certificate is scoped to a tenant and a machine; it does not carry a product, an artifact, or a plugin format.
  • Delivery layer (host-specific): Packaging conventions, installation paths, host lifecycle, and the client experience for one kind of software. OFX plugins for post-production hosts are the kind served today, delivered through MCNexus on macOS and Windows.
  • End users use MCNexus to activate licenses, install software, check for updates, install previous versions, and perform rollback.
  • Developers use configured licensing, Commerce, release, and communication integrations.

OpenKey is the License Provider maintained as part of Nexus. Commerce manages offers, orders, payments, and fulfillment. Email verification codes and Google sign-in work alongside GitHub for user identity in the OpenKey and Commerce flows described below, while GitHub remains the current source for release artifacts.

The planned architecture allows other identity, licensing, payment, email, and release providers, with GitHub becoming optional as a release host as well. Additional kinds of software outside OFX are planned work and are not served by MCNexus today; the self-contained SDK mode that lets a product activate a license without MCNexus in the loop is implemented and covered by the finalized third-party binary license, while full self-service onboarding remains part of the planned work listed below. Planned SaaS work adds external organizations, access control, onboarding, service billing, and tenant isolation.

Implemented Capabilities

Desktop Experience and Distribution

  • ✓ Official Windows distribution: MCNexus is available from the Microsoft Store, the official and recommended Windows channel, with Store-managed distribution and automatic background updates. A direct installer remains available as an alternative, with the signing limitation described above.
  • ✓ Native macOS and Windows applications: platform-specific clients for license activation, plugin management, update detection, installation of previous versions, and rollback.
  • ✓ OFX installation and removal: automatic installation in native system locations, explicit separation between license and plugin actions, installation recovery, and transparent uninstall behavior.
  • ✓ Clear operational states: users can distinguish active and inactive licenses, unavailable products, missing plugins, local problems, updates, and rollback options.
  • ✓ Quiet background synchronization and resource awareness: periodic license checks run in spaced background batches without interrupting active host playback or rendering, monitor network availability passively and wait for connections to stabilize before reconnecting, display a clear warning with an immediate resync button if an offline tolerance window expires, pause background checks while minimized to the tray or menu bar, and restore state immediately when the window returns.
  • ✓ Distributing DCTLs as OFX plugins: DCTL color scripts and LUTs can be packaged into installable OFX plugins inside an encrypted bundle run by a universal player, allowing creators to distribute and license effects through MCNexus without building a plugin from scratch. Native support across major Windows GPU vendors and platform-managed key protection remain in current and planned work.
  • ✓ External MIDI controller support (NexControl): hardware control support for compatible OFX plugins across macOS and Windows with native tray and menu-bar status controls, built-in controller profiles alongside customizable user mappings, responsive host viewer updates, and automatic active-node focus tracking on both macOS and Windows.

Licensing and Release Platform

  • ✓ OpenKey and Cryptlex support: the Nexus-native OpenKey backend issues the license for a free product and for a paid one, through the same client experience as the alternative Cryptlex backend. Both do hardware-bound, node-locked activation.
  • ✓ Multi-product and entitlement-aware licensing: distinct products, editions, plugins, and multiple licenses from the same tenant remain separated through activation, synchronization, caching, and installation.
  • ✓ Release channel separation (stable and beta): the backend strictly routes standard, trial, and demo licenses to stable releases only, ensuring prereleases are delivered exclusively to beta licenses. A user-facing channel toggle inside the desktop application remains in Current Work.
  • ✓ Protected release delivery: platform-specific artifacts, authenticated download resolution, secure streaming, version discovery, and rollback without exposing license keys.
  • ✓ Package integrity: downloaded plugin packages are verified before installation. Each release carries a manifest declaring its assets and their client requirements, and downloads are refused when a client does not meet them; beyond that, every asset is published with a SHA256 digest that the application checks against the downloaded file before installing. A package whose digest does not match is refused and discarded, never installed. Validating explicit mismatch-rejection scenarios and enforcing strict digest checks on beta builds as well remain part of ongoing release validation.
  • ✓ Aggregated device synchronization: multiple licenses can be checked and renewed in one request while preserving their independent lifecycle.
  • ✓ Offline validity window: an activation certificate carries two independent deadlines: when renewal starts being attempted, and the hard limit the SDK itself enforces. The default window is 30 days, configurable per license up to 365, and the issuer guarantees it always covers at least two whole renewal attempts, so a single failed sync can never be what denies a license.
  • ✓ Offline activation for machines with no network: a machine can export an activation request, receive a certificate issued elsewhere, and install it without ever reaching the network; the same path releases the seat again with a deactivation proof. Certificates are verified against the product's keyring on import and on every load afterwards, so this route weakens nothing. Used for air-gapped installations, and the same mechanism the recovery path in Continuity relies on.
  • ✓ Developer-held recovery authority: an offline Ed25519 recovery key generated by the developer whose private half never reaches Nexus servers, allowing emergency certificates to be issued and accepted by installed products with no Nexus infrastructure involved.
  • ✓ Public client SDK (NexKeyRuntime): a native C/C++ SDK for update discovery, product notices, and offline verification of activation certificates, published at github.com/ciqueira/NexKeyRuntime. Its public contract (the C header, JSON definitions, examples, and integration documentation) is Apache-2.0, and compiled static libraries for macOS (universal) and Windows (x64, x86, and ARM) are published as releases with checksums. The public API is stable as of 1.0, evolving additively under the compatibility policy published in the repository.
  • ✓ Binary license for third parties: the license governing compiled NexKeyRuntime releases (BINARY_LICENSE.md) is finalized, clearing the published binaries for use by developers outside Nexus. Linking the binary into your own product is free under any Nexus plan, including the free Comunidade plan; a commercial plan is only required if the product you ship charges its own end users. The repository's own contents remain Apache-2.0 and usable today.
  • ✓ Local Developer Sandbox (Phase 1): an isolated test environment offering pre-provisioned test keys, a reference OFX plugin, a command-line testing utility, and the DCTL effect packager so developers can verify licensing, updates, notices, and MIDI control locally before formal onboarding. A guided interactive web checkout demo remains under Current Work.

Commerce and Customer Operations

  • ✓ Provider-neutral Commerce foundation: identity, payment, licensing, fulfillment, delivery, and email are separated by explicit contracts instead of being tied to one checkout composition.
  • ✓ Flexible buyer and user identity (Email verification, Google, and GitHub): customers can claim free licenses or complete commercial purchases using a verified email code or a Google account without needing a GitHub account, alongside GitHub sign-in.
  • ✓ Authenticated Stripe purchase flow: verified buyer identity (email code, Google, or GitHub), duplicate-purchase protection, environment-scoped payment accounts, multi-currency Prices, duplicate-safe fulfillment, automatic in-place upgrade from evaluation to full editions on the same license key, and protected key reveal.
  • ✓ Operational purchase records: offers, orders, payments, support benefits, fulfillment, and email delivery are managed separately from the technical license and are visible in the Back Office.
  • ✓ Auditable customer communication and legal evidence: operational messages avoid duplicate delivery, support controlled resend, and preserve the document versions, locale, consent, and transaction references attached to each Commerce order.

Platform Operations and Security

  • ✓ Internal multi-tenant Back Office: products, tenants (including standardized tenant creation and tenant archival), releases, licenses, activations, payment accounts, Commerce Offers, and operational history are managed through protected administrative access.
  • ✓ Resilient release metadata caching: multi-layer metadata caching protects desktop update discovery and artifact downloads from upstream release-host rate limits.
  • ✓ Security controls: encrypted tenant configuration, secure session tokens, protected license payloads, rate limiting, network-edge controls, security headers, and structured audit records.
  • ✓ Controlled delivery pipeline: backend changes and verification procedures follow versioned staging and promotion gates. macOS and Windows packages are produced as platform-specific artifacts through versioned release workflows.
  • ✓ Operational documentation: bilingual user, developer, legal, support, and troubleshooting documentation accompanies the platform.

Current Work

Current work covers code signing, cross-platform consistency, expanded Commerce operations, and interactive developer evaluation.

  • ○ Code signing and release validation: sign the direct Windows installer, sign and notarize the macOS application, validate Gatekeeper and SmartScreen behavior, complete negative download-integrity verification, and test releases on clean machines. The Microsoft Store remains the official Windows channel during this work.
  • ○ License lifecycle consistency and platform parity: complete activation-reuse validation and add a beta opt-in toggle in the desktop interface.
  • ○ Commerce production coverage, service billing, and legal operations: expand controlled live validation across payment methods, currencies, Radar review, delivery, support benefits, logs, and recovery scenarios; add automated refund and dispute workflows, structured developer plan modeling and enforcement, billing-country visibility, financial exports, electronic cancellation, and the required legal and accounting launch reviews.
  • ○ Interactive Web Sandbox (Phases 2 and 3) and commercial DCTL package hardening: deliver the guided desktop and test-checkout walkthrough for evaluating developers; expand native GPU compatibility across major vendors on Windows and add platform-managed content key protection for commercial packages.

Planned: Software Protection and Intellectual Property

This work advances beyond transport and container security into runtime IP protection, raising the cost of unauthorized binary tampering without impacting host stability or real-time playback performance.

  • ○ Expanded Asset & Shader Vault: extend the encrypted effect container with native graphics compilation across all major GPU vendors on Windows, platform-managed content key protection tied directly to an active license, and strict in-memory lifetime cleanup so unprotected effect code never touches disk.
  • ○ Crypto-bound execution: replace simple allow-or-deny license checks with functional dependencies between verified, machine-bound activation certificates and essential processing constants, color transforms, or effect coefficients so algorithms only compute legitimate output when properly authorized.
  • ○ Hardware-backed workstation binding: anchor node-locks to dedicated hardware security capabilities available on modern macOS and Windows systems to resist machine identity cloning and virtualized spoofing.
  • ○ Runtime anti-tampering and binary integrity: harden compiled plugin binaries against automated reverse engineering and unauthorized runtime code modifications.

Planned: Desktop Experience and Studio Workflows

  • ○ Batch management (Update All and Install All): centralized background queue in MCNexus to download and verify multiple licensed plugins in parallel, with sequential and host-safe installation when host applications are closed.
  • ○ Studio profile and version locking: project-level and suite-level version pinning, enabling multi-seat post-production studios to freeze plugin versions across an entire facility during long-form projects and avoid accidental updates during active deliveries.
  • ○ Elastic licensing and render passes (Guest Pass & Overdraft): safeguards to prevent missed delivery deadlines and accidental watermarks during production render spikes. Enables issuing temporary cryptographic guest passes for dedicated render nodes or freelance assistants (including headless background rendering without a graphical interface), alongside pre-approved emergency license burst capacity (overdraft) reconciled later through local cryptographic receipts.
  • ○ Two-way MIDI controller feedback and expanded hardware support: send active plugin parameter values back to motorized faders and LED encoder rings, and broaden studio control-surface compatibility.

Planned: Self-Service

  • ○ Customer portal: with email verification and Google sign-in already live, allow customers to view purchases and licenses, manage activations, recover access, release permanently lost or unresponsive machines without manual support, and contact the right support channel. Moving a license between reachable machines already works self-service online and air-gapped; what this adds is self-service recovery when the previous workstation is gone or dead.
  • ○ Plugin health checks and notice persistence: detect and report missing, incompatible, incomplete, or locked installations as well as host version and architecture mismatches, and remember dismissed or snoozed product notices across sessions.
  • ○ Developer integration kit and publishing tools: build on the published guides and Local Sandbox (Phase 1) with Back Office release-manifest editing and validation tools, automated update-announcement triggers, and continuous cross-platform integration test suites.
  • ○ Additional identity, checkout, and email providers: email verification and Google sign-in already run alongside GitHub; remaining work adds optional sign-in providers (such as Microsoft and Apple), normalized alternative checkout providers, and independent transactional email routing.
  • ○ Flexible release storage: extend release artifact delivery with developer-owned S3-compatible and Cloudflare R2 storage without altering client verification or rollback.
  • ○ Developer publishing and tenant lifecycle: build on existing tenant archival with standardized onboarding workflows, publication checklists, automated retention cleanup, and full tenant data exports.

Planned: Continuity and Tenant Portability

Continuity and Recovery documents the continuity architecture, active safeguards, and covered scenarios.

  • ○ Tenant data and artifact portability: provide documented, versioned exports of products, releases, licenses, entitlements, and activation records, while allowing developers to retain and redistribute their own verified release artifacts.

Planned: Beyond OFX

The licensing core is host-independent, but serving a new kind of software is more than licensing: it needs packaging conventions, installation paths, host lifecycle handling, and a client experience. None of the items below is available today, and no order or date between them is committed.

  • ○ Professional audio plugin formats: packaging and native installation adapters for audio DSP plugins (VST3, Audio Units, AAX), providing audio developers a modern, dongle-free alternative to legacy copy protection.
  • ○ Language bindings for the C SDK: first-party bindings for .NET, Python, Rust, and Swift built over the stable C interface of NexKeyRuntime, enabling studio pipeline tools, scripts, and standalone applications to use Nexus licensing.
  • ○ Host-independent activation (standalone SDK) for third parties: self-service onboarding and project credential provisioning for developers shipping their own custom installers without MCNexus as the delivery client.
  • ○ Linux support: workstation and render node execution, currently limited by machine identification and platform lifecycle rather than the licensing core.

Planned: SaaS Preparation

This work is required before an external developer organization can configure and operate products through the service.

  • ○ Organizations, membership, and RBAC: introduce an Organization/Seller boundary with owners, members, roles, and least-privilege access to products and operations.
  • ○ Developer portal and onboarding: provide guided organization, seller, product, provider-account, legal-profile, and release setup with validation before production activation.
  • ○ Tenant ownership and isolation: bind products, credentials, payment and email accounts, legal evidence, and audit history to an organization; add authorization, key rotation, and cross-tenant isolation tests.
  • ○ Self-service legal configuration: support versioned seller and product documents, controlled inheritance, publication history, consent evidence, and environment-specific launch gates.
  • ○ Nexus service billing: enforce plans, quotas, usage measurement, trial and subscription lifecycle, and billing for the Nexus service independently from Commerce transactions made by each plugin seller.
  • ○ SaaS legal and operational package: establish the service agreement, DPA, subprocessor list, acceptable-use policy, support policy, SLA/SLOs, incident response, data export, and termination process.
  • ○ Service resilience: provide per-organization auditability, observability, backup and restore verification, capacity controls, and documented recovery objectives.

Under Consideration

These directions are evaluated after the preceding milestones and do not represent commitments to a particular provider or date.

  • ○ Local network floating seats (LAN Floating Pool) for dynamic license sharing across render farms and editing suites without continuous internet access.
  • ○ International Commerce capabilities such as regional pricing, expanded currency reporting, and market-specific tax support where operationally required.
  • ○ Privacy-conscious, opt-in crash reporting and product insights for participating developers.

The candidates above assume provider accounts connected directly by Nexus for its own service or by each plugin seller for their products. A Nexus-operated marketplace, aggregated Merchant of Record account, and shared seller-funds model are outside the current scope.

Development Principles

  • Validate a complete operational flow before expanding it to more products or providers.
  • Preserve provider-neutral domain boundaries and avoid making customer rights depend on a third-party provider's internal state.
  • Keep distribution independent of a single sales channel, licensing backend, payment provider, email provider, or release host.
  • Maintain backward compatibility for public links, licenses, releases, and audit history through explicit updates.
  • Treat tenant isolation, security, privacy, and recoverability as product requirements rather than later infrastructure work.
  • Promote work by milestone evidence and launch gates; priorities may change as production findings and developer feedback are validated.
