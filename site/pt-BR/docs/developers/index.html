Documentação para Desenvolvedores

O Nexus fornece infraestrutura para licenciar, distribuir e atualizar software. Esta página é o roteiro comum de entrada e handoff para desenvolvedores: reúne as informações necessárias para avaliar o projeto, configurar o tenant e retornar os valores específicos para integrar o NexKeyRuntime.

Use o mesmo intake para plugins, aplicativos desktop e outros produtos. A integração OFX é a única integração de host atualmente em produção. Outros hosts e tipos de produto podem ser propostos, mas passam por avaliação técnica antes da confirmação de suporte ou prazo; consulte o Roadmap.

Processo atual: as integrações são avaliadas e configuradas manualmente, por projeto. Ainda não existe uma API pública de onboarding nem criação self-service de tenants. O roteiro abaixo é uma coleta inicial, não uma promessa de que todo host, provider ou fluxo solicitado já seja suportado.

2. Modelos de distribuição

Dois backends de licenciamento são suportados. O OpenKey é o padrão nativo do Nexus: emite a licença de um produto gratuito e de um pago, e é por onde o fluxo Nexus Commerce atual emite as licenças. O Cryptlex é uma alternativa para projetos que já utilizam o Cryptlex como plataforma de licenciamento, ou que optam por um provedor terceiro dedicado em vez do nativo do Nexus. Os dois fazem ativação vinculada ao hardware, por node-lock; isso não é o que os diferencia.

OpenKey

O backend nativo do Nexus. A mesma emissão serve um produto gratuito e um pago; o que muda é como o usuário recebe a chave.

Para projetos gratuitos/open source, as licenças OpenKey são obtidas por um link Obter chave, disponibilizado para cada plugin integrado. Ao acessar o link, o usuário autoriza a identificação pela conta do GitHub. O e-mail principal verificado é utilizado para gerar a licença e exibir a chave que será inserida no MCNexus. Se o mesmo usuário acessar novamente o link, a chave já associada à conta será apresentada.

Para projetos comerciais, o OpenKey também emite a licença dentro do fluxo Nexus Commerce atual: o GitHub confirma a identidade, o Stripe processa o pagamento, o OpenKey cria ou atualiza a licença, e o MailerLite entrega a mensagem operacional. Ver §5.

Node-lock por fingerprint de máquina, as edições Beta/Demo/Trial/Full, a janela de validade offline e a ativação air-gap fazem parte do núcleo de licenciamento OpenKey, seja o produto gratuito ou pago.

Uma conta do GitHub com e-mail principal verificado é necessária no fluxo atual. Tornar o GitHub um adapter opcional de identidade e origem de releases faz parte da evolução planejada.

Cryptlex

Um backend alternativo para projetos que já utilizam o Cryptlex como plataforma de licenciamento, ou que optam por um serviço terceiro dedicado em vez do nativo do Nexus. Ativação vinculada ao hardware, por node-lock, não é o que diferencia o Cryptlex; o OpenKey faz isso também (acima); a diferença é que o Cryptlex é uma plataforma externa utilizada diretamente em alguns produtos, com painel e ferramentas fora do Nexus. O MCNexus valida e ativa contra uma chave emitida pelo Cryptlex da mesma forma que faz com o OpenKey.

A venda e a emissão da licença de produtos licenciados pelo Cryptlex acontecem pelo canal comercial externo do próprio desenvolvedor. Edições e limites de ativação de produtos Cryptlex são configurados diretamente na conta Cryptlex do desenvolvedor, não pelo Nexus. Um checkout Stripe emitindo uma licença Cryptlex automaticamente está no roadmap.

As condições comerciais, o número de ativações, as edições disponíveis e a política de suporte são definidos para cada produto.

3. Ciclo de integração

O processo começa com a análise do formulário do projeto e a confirmação do que já é suportado. Em seguida, são definidos o perfil de integração e a configuração do tenant, entregues os valores de handoff da SDK descritos em §7 e validada uma release real antes da conclusão do onboarding.

3.1. Primeiro contato

Preencha o formulário do projeto em §1. Informações adicionais podem ser solicitadas caso o host, perfil de licenciamento, provider ou formato de release demande avaliação técnica.

3.2. Preparação dos arquivos

As regras de empacotamento abaixo se aplicam à integração OFX atual. Para outros tipos de produto, os formatos suportados são definidos durante a avaliação técnica. Para OFX, cada versão deve fornecer um artefato para cada sistema operacional suportado. O macOS aceita .zip ou .pkg; o Windows requer .zip. Use a seguinte convenção de nomes:

<Produto>-macOS-<Versão>.zip
<Produto>-macOS-<Versão>.pkg
<Produto>-Windows-<Versão>.zip

Exemplos:

MeuPlugin-macOS-1.2.0.zip
MeuPlugin-macOS-1.2.0.pkg
MeuPlugin-Windows-1.2.0.zip

Mantenha o nome do produto, a plataforma e a versão claramente identificados. Evite publicar um único arquivo para mais de uma plataforma.

O conteúdo recomendado do ZIP possui o bundle OFX na raiz:

MeuPlugin-macOS-1.2.0.zip
└── MeuPlugin.ofx.bundle/
    └── Contents/
        └── MacOS/

MeuPlugin-Windows-1.2.0.zip
└── MeuPlugin.ofx.bundle/
    └── Contents/
        └── Win64/

Cada ZIP deve conter somente o bundle correspondente à respectiva plataforma, posicionado na raiz do arquivo. O nome do bundle e do executável OFX deve permanecer consistente entre versões.

Para um .pkg de macOS, o MCNexus expande o pacote em uma pasta temporária e procura diretórios .ofx.bundle no payload, sem executar scripts de instalação do pacote. O bundle deve ser autocontido e instalável por cópia para o diretório de plugins OFX; pacotes que dependem de scripts de instalação não são suportados.

3.3. Publicação

Com os arquivos preparados, o plugin é configurado no Nexus e testado no MCNexus. Depois da publicação, novas versões podem seguir o mesmo padrão de nomes e empacotamento.

4. Canais e edições

  • OpenKey: Beta, Demo, Trial e Full: as mesmas quatro edições num projeto gratuito ou pago.
  • Cryptlex: edições e limites de ativação são configurados diretamente na conta Cryptlex do desenvolvedor; o Nexus não os determina.

4.1. Papel de cada edição no OpenKey

  • Demo (avaliação sem prazo): versão de avaliação funcional sem data de expiração. O usuário obtém uma chave gratuita via Get Key e instala o plugin pelo MCNexus; o plugin lê NEXKEYRUNTIME_EDITION_DEMO no snapshot da SDK (snapshot.edition_enum) e aplica marca d'água ou limitação funcional/de resolução.
  • Trial (avaliação com prazo): versão de avaliação com janela de expiração (trial_days), iniciando a contagem regressiva automaticamente no momento da primeira ativação na máquina.
  • Full (edição completa): edição comercial ou desbloqueada sem restrições de avaliação.
  • Beta (testes fechados): edição restrita a testes controlados pelo desenvolvedor. Por regra de segurança, licenças Beta são bloqueadas contra emissão via checkout Stripe.

4.2. Canais de release (stable vs. beta)

  • Gate ativo hoje no backend: licenças nas edições Full, Trial e Demo recebem estritamente releases do canal stable, evitando que uma prerelease do GitHub seja entregue por engano a clientes de produção. Apenas licenças emitidas com a edição Beta recebem artefatos marcados como canal beta (prerelease).
  • Integridade de versão e interface do cliente: cada versão publicada deve possuir identificação inequívoca e não deve ser substituída silenciosamente por outro binário com o mesmo número. O roteamento de canal é aplicado pelo backend conforme a edição da licença; ainda não há seletor ou filtro visual de canal Beta dentro da interface dos aplicativos desktop MCNexus.

5. Fluxo Nexus Commerce atual

O Commerce vende um produto diretamente pela conta Stripe do próprio desenvolvedor, com 0% de comissão da plataforma e emissão, upgrade na mesma chave e entrega da licença automatizados.

5.1. Arquitetura de checkout e fulfillment ponta a ponta

Configurado uma única vez por produto: um catálogo de ofertas vinculando um preço ao produto e à edição-alvo, a conta Stripe do desenvolvedor e as URLs de Termos de Uso, Política de Privacidade e Política de Reembolso apresentadas no checkout.

A cada venda:

  1. Identidade: hoje o GitHub OAuth verifica a identidade e o e-mail principal do comprador. Código OTP / magic link por e-mail e OAuth Google/Microsoft (sem exigir conta no GitHub) estão no roadmap.
  2. Checkout Stripe na conta do desenvolvedor: o cliente conclui o pagamento diretamente na conta Stripe do próprio desenvolvedor (sem custódia intermediária da receita pelo MCNexus).
  3. Registro auditável de pedido e aceite jurídico: o Nexus registra o pedido, o evento de pagamento e qual versão dos Termos de Uso, Política de Privacidade e Política de Reembolso o comprador aceitou no checkout.
  4. Fulfillment idempotente e entrega: as tentativas de fulfillment são registradas por pedido para que um evento de pagamento reenviado ou duplicado nunca emita uma segunda licença. O OpenKey cria ou promove a licença, e a chave é entregue imediatamente em tela por revelação única (one-time reveal) acompanhada de e-mail transacional via MailerLite.
  5. Ativação na estação de trabalho: o cliente insere ou sincroniza a chave no MCNexus, que valida o acesso e instala ou destrava o artefato correspondente.

*Impostos sobre venda (IVA e sales tax): como o pagamento corre diretamente na conta Stripe do desenvolvedor, o cálculo, recolhimento e declaração de IVA / sales tax ficam sob responsabilidade do desenvolvedor (por exemplo, via Stripe Tax). Provedores que atuam como Merchant of Record* (como o Lemon Squeezy, previsto no roadmap) assumem essa obrigação tributária em nome do vendedor. Esta distinção é operacional e não constitui aconselhamento fiscal.

5.2. Transição de Demo ou Trial para Full

  • Transição automática via Commerce (mesmo e-mail): quando o usuário final obtém uma licença Demo ou Trial gratuita (via Get Key) e depois compra a edição Full no Checkout Stripe utilizando o mesmo e-mail verificado, o Nexus Commerce promove automaticamente a licença existente (upgradeEdition) para Full. O sistema remove a data de expiração (expires_at / trial_days), atualiza o limite de máquinas (max_activations) e preserva a mesma chave e o plugin já instalado na estação de trabalho. Na próxima sincronização do MCNexus (ou renovação em segundo plano da SDK), o certificado local muda para NEXKEYRUNTIME_EDITION_FULL e destrava o plugin sem reinstalar arquivos e sem quebrar projetos salvos no host (.drp).
  • Transição por ação manual suportada (outro e-mail ou upgrade via backoffice): caso o usuário compre uma nova chave Full usando outro endereço de e-mail, basta substituir a chave no aplicativo MCNexus sem precisar reinstalar os arquivos do plugin no disco. Da mesma forma, quando um administrador promove uma licença pelo backoffice, basta clicar em Sincronizar no MCNexus para atualizar o certificado local para Full.

5.3. Divisão de responsabilidades

  • O MCNexus opera: verificação de identidade do comprador, orquestração da sessão de checkout, registro auditável do aceite jurídico, emissão e upgrade idempotente de licença (Demo/Trial → Full), envio de e-mail transacional e instalação protegida, atualização e rollback do binário pelo aplicativo desktop.
  • O desenvolvedor responde por: código e estabilidade do produto, definição de preços e ofertas na própria conta Stripe, aplicação das restrições de avaliação dentro do plugin quando snapshot.edition_enum indicar Demo ou Trial, obrigações fiscais sobre as vendas na conta Stripe e suporte funcional da ferramenta.

Produtos licenciados pelo Cryptlex são distribuídos pelo MCNexus com uma chave comercial válida, com a emissão feita na conta Cryptlex do próprio desenvolvedor. O fulfillment por Cryptlex dentro deste fluxo, e providers adicionais de pagamento, licenciamento, identidade, e-mail e releases, estão no roadmap.

As integrações devem tratar reenvios e eventos duplicados sem emitir licenças indevidas. Chaves, tokens, assinaturas de webhook e credenciais de serviço nunca devem ser armazenados em repositórios públicos.

6. Segurança e distribuição

O Nexus utiliza downloads protegidos para produtos que exigem controle de acesso. A chave de licença não deve ser incorporada a URLs públicas, logs, nomes de arquivo ou relatórios de erro.

Assinatura e verificação criptográfica de todos os pacotes distribuídos fazem parte da evolução prevista no Roadmap.

7. NexKeyRuntime: integração e handoff

O NexKeyRuntime é a SDK pública em C/C++14 que um produto embarca, cobrindo descoberta de atualizações, avisos de produto e verificação offline de um certificado de ativação: na render thread a decisão é uma única leitura atômica, sem rede, sem I/O de arquivo e sem parsing de JSON.

O repositório publica o contrato público: o header C, schemas JSON, documentação de integração e exemplos. As bibliotecas oficiais compiladas são distribuídas separadamente sob a licença dos binários. Confirme os termos aplicáveis e o acesso aos binários das plataformas necessárias durante a configuração do projeto; o repositório público de código por si só não concede um tenant nem acesso ao backend.

7.1. Escolha do perfil de integração

  • Perfil A (MCNexus ativa): O cliente insere ou obtém a licença no MCNexus. O host ativa e grava um recibo local; o produto incorpora o NexKeyRuntime para verificar esse recibo e tomar a decisão local de licença. Este é o perfil comum para plugins.
  • Perfil B (o produto ativa): O próprio produto coleta a chave de licença e chama a API de ativação da SDK. A escolha exige uma avaliação explícita do backend e do fluxo do usuário.

O handle de updates e avisos da SDK é independente dos dois perfis de licenciamento. Um produto pode solicitar verificação de licença, updates e avisos, ou ambos.

7.2. O que o MCNexus retorna para a integração

Depois de definidos o tenant e a configuração do produto, o desenvolvedor recebe os valores aplicáveis ao projeto por um canal privado:

  • tenant_id: identificador exato do tenant que deve ser passado à SDK.
  • ProductData: configuração assinada do produto, com o endereço base do serviço e o keyring de chaves públicas. Não contém chave privada de assinatura e pode ser incorporado ao produto, inclusive em um repositório público.
  • variant / entitlement: valor exato para passar a nexkeyruntime_license_set_variant(), por exemplo download:sample. Deve corresponder ao entitlement configurado para o produto e para a licença; não é inferido do ProductData.
  • Configuração de updates/avisos, se solicitada: artifact_id, base_url do serviço e os valores acordados de plataforma, arquitetura, canal e versão. Esses campos são separados do variant da licença.
  • Detalhes dos binários da SDK, se necessários: release/versão oficial, bibliotecas das plataformas aplicáveis e checksums, licença dos binários e instruções de build e integração correspondentes.
  • Configuração testada: perfil verificado, fluxo de ativação esperado e release/artefato usado no teste da integração.

O mesmo ProductData pode ser reutilizado entre variantes de um tenant, mas a SDK ainda precisa receber o tenant_id e o variant exatos em runtime. Para o handle de updates, utilize o artifact_id específico e os metadados de release conforme o guia da SDK.

Nunca envie nem incorpore uma chave privada de assinatura do tenant, uma credencial de backend ou um segredo de serviço. O MCNexus não precisa entregar esses segredos para integrar a SDK.

Três pontos importam antes de planejar uma integração:

  • Binários compilados. O conteúdo do repositório público está sob Apache-2.0. Os binários oficiais compilados possuem termos próprios; revise a licença de binários e confirme o acesso às releases necessárias durante o onboarding.
  • A API é estável desde a 1.0. Função, layout de struct ou código de resultado que já existe nunca muda de um jeito que quebre um binário já compilado: em 1.x só entra mudança aditiva, e quebra de compatibilidade exigiria 2.0. Os códigos de resultado são append-only e nunca são reutilizados nem renumerados.
  • Dois perfis de integração. No Perfil A, o MCNexus ativa e o produto verifica localmente. No Perfil B, o próprio produto ativa via SDK e exige avaliação por projeto do backend e do fluxo do usuário. Nenhum dos dois perfis é provisionado por autoatendimento hoje.

O Roadmap acompanha os três.

8. Providers integrados

Cada camada abaixo é separada por um contrato explícito, então um provider é uma configuração da plataforma, e não algo embutido. Esta tabela é a fonte única do que está conectado hoje; as outras páginas descrevem a camada, não o fornecedor.

Camada Integrado hoje No roadmap
Identidade GitHub OAuth E-mail e magic link, sem conta no GitHub
Pagamento Stripe Lemon Squeezy, e outros checkouts depois
Licenciamento OpenKey (nativo do Nexus), Cryptlex Keygen, LicenseSpring
Fulfillment do Commerce OpenKey Cryptlex
E-mail transacional MailerLite Um provider adicional, sob contratos separados
Origem de releases GitHub Releases; releases hospedados pelo Cryptlex nos produtos configurados com Cryptlex Storage compatível com S3, Cloudflare R2 primeiro

Os itens de roadmap são direções, não compromisso com fornecedor ou data: o Roadmap carrega o estado atual de cada um.

9. Próximos passos

A relação de plugins atuais está no Discovery. Projetos open source podem ser enviados pelo formulário público de sugestão.

Para integrações comerciais, entre em contato de forma privada pelo e-mail hello@mcnexus.app. Não publique modelos comerciais, credenciais, valores ou outros detalhes confidenciais no GitHub Issues.

O kit público de integração, a expansão de providers, a distribuição independente do canal comercial, os exemplos e as especificações automatizadas permanecem no Roadmap.
