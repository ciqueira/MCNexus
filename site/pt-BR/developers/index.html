Integração

Duas formas de integrar.

O produto embarca a SDK nativa e ativa a própria licença, ou o aplicativo MCNexus ativa na estação de trabalho. Os dois caminhos usam o mesmo núcleo — certificado Ed25519 com escopo de tenant e máquina, verificado localmente contra um keyring compilado no produto.

Ver planos e preços NexKeyRuntime no GitHub ↗

A primeira decisão

Perfil A ou Perfil B.

A diferença é quem ativa a licença. O resto do núcleo — offline, air-gap, edições, updates, avisos, continuidade — é o mesmo nos dois.

Perfil A

O MCNexus ativa a licença.

O aplicativo para macOS e Windows ativa a licença, baixa o produto, instala, atualiza e faz rollback na estação de trabalho. O produto embarca a SDK apenas para verificar o certificado localmente e ler a decisão de licença.

Aplica-se a plugin OFX em host de pós-produção. Dispensa escrever, assinar e distribuir um cliente próprio.

Guia de operação →

Perfil B

O produto ativa a própria licença.

O produto com instalador próprio linka a SDK e ativa, sincroniza e desativa por conta própria, sem aplicativo cliente no caminho. A SDK detecta processo com interface e processo headless, para servidor ou render farm.

Aplica-se a software nativo fora de OFX. A configuração é definida projeto a projeto.

Código

O ciclo em três trechos.

API real do header público do NexKeyRuntime, não pseudocódigo. Os exemplos completos estão no repositório da SDK.

/* 1. Ativar — Perfil B, a partir do próprio produto. */
NexKeyRuntimeLicenseHandle *license = nexkeyruntime_license_create();
nexkeyruntime_license_set_product_data(license, PRODUCT_DATA);
nexkeyruntime_license_set_tenant_id(license, "tenant-id");
nexkeyruntime_license_set_variant(license, "download:entitlement");
nexkeyruntime_license_load_local(license);

O PRODUCT_DATA é um blob emitido pelo backoffice para o tenant. Contém um keyring público e uma URL base — nenhum segredo.

/* 2. Decidir, na thread de render.
      Sem lock, sem alocação, sem syscall, sem rede. */
if (nexkeyruntime_license_render_decision(license)
        == NEXKEYRUNTIME_RENDER_ALLOW) {
    render(frame);
}

É a única chamada segura dentro de um callback de render. A licença já foi resolvida antes, fora do caminho crítico.

/* 3. Estado da licença, fora do caminho crítico. */
NexKeyRuntimeLicenseSnapshot snapshot;
snapshot.struct_size = sizeof(snapshot);

if (nexkeyruntime_license_get_snapshot(license, &snapshot)
        == NEXKEYRUNTIME_OK) {
    printf("license status: %d\n", (int)snapshot.status);
}

nexkeyruntime_license_destroy(license);

A mesma estrutura reporta a edição da licença. Quem aplica o limite de uma edição é o integrador.

Plataforma

O que está incluído.

Cada item aponta a seção da documentação que o detalha.

  • Ativação node-lock: certificado Ed25519 assinado por uma chave com escopo de um único tenant e preso ao fingerprint da máquina, com limite de vagas por licença e desativação em autoatendimento. Dois backends emitem a licença: o OpenKey, nativo, e o Cryptlex, para quem já o usa. Modelos de distribuição →
  • Offline e air-gap: o certificado carrega dois prazos independentes — syncAfter, quando a thread em segundo plano começa a tentar renovar, e offlineValidUntil, o limite rígido que a SDK aplica. O emissor garante que a janela offline cubra pelo menos duas tentativas inteiras de renovação, então uma sincronização com falha nunca é o que nega uma licença. Por que uma interrupção não é uma negação →
  • NexKeyRuntime: C/C++14 com ABI C estável, macOS universal (arm64 e x86_64) e Windows x64. O repositório publica o contrato completo sob Apache-2.0 — header C, JSON Schemas, documentação e exemplos. A API está em 0.x; os códigos de resultado são append-only por política. SDK de cliente →
  • Cliente MCNexus: ativa, instala, atualiza e faz rollback na estação de trabalho. Ativar, desativar, remover a chave local e remover os arquivos do plugin são operações independentes. Guia de operação →
  • Posse de chave e continuidade: o keyring comporta até quatro chaves, e uma chave aposentada continua nele e apenas para de assinar — por isso a rotação não invalida o instalado. A chave de recuperação é gerada pelo desenvolvedor, e um envio que contenha a metade privada é recusado. Se o operador não estiver mais disponível →
  • Distribuição e rollback: proxy de download com token assinado de vida curta — o aplicativo nunca recebe a URL real do release. Pacotes por plataforma, descoberta de versão e reinstalação de uma versão publicada anterior. Segurança e distribuição →
  • Edições e entitlements: beta, demo, trial e completa — trial tem prazo, demo não. O escopo de ativação é único por tenant, fingerprint e entitlement: a mesma máquina não ocupa duas vagas do mesmo direito. Canais e edições →
  • Commerce e fulfillment: as vendas correm pela conta Stripe do próprio desenvolvedor. Cada venda registra o pedido, o evento de pagamento e qual versão dos termos o cliente aceitou; as tentativas de fulfillment são registradas por pedido, então um evento reenviado não emite uma segunda licença. Fluxo Nexus Commerce →
  • Avisos no produto: severidades critical, recommended e info, conteúdo localizado e segmentação por host, faixa de versão, plataforma e arquitetura. O conteúdo é texto: HTML, Markdown arbitrário e script ficaram fora por decisão de escopo. Updates e avisos ↗

Primeiro contato

Como começar.

Não existe cadastro nem painel de autoatendimento. Cada integração é revisada e configurada projeto a projeto — o onboarding self-service está no roadmap.

  1. Descrição do produto

    Nome, plataformas suportadas, distribuição gratuita ou comercial, e o backend de licenciamento: OpenKey ou Cryptlex.

  2. Preparação dos arquivos

    Empacotamento por plataforma e nomes de release seguindo o padrão descrito na documentação, para que a descoberta de versão funcione.

  3. Publicação

    O produto é configurado no Nexus e testado ponta a ponta. Depois disso, novas versões seguem o mesmo padrão de nomes e empacotamento.

Roadmap

O que ainda não é self-service.

O conteúdo do repositório do NexKeyRuntime é Apache-2.0 e utilizável hoje. O acesso aos binários compilados é combinado com cada desenvolvedor, sob a licença dos binários, e a API está em 0.x — os códigos de resultado nunca são reutilizados nem renumerados, mas a superfície ainda pode evoluir.

O portal do cliente, o storage próprio do tenant, os avisos agendados e a entrada self-service são itens do roadmap público, com o estado de cada um mantido lá.
