Integration

Two ways to integrate.

The product embeds the native SDK and activates its own license, or the MCNexus app activates it on the workstation. Both paths use the same core — an Ed25519 certificate scoped to a tenant and a machine, verified locally against a keyring compiled into the product.

See plans and pricing NexKeyRuntime on GitHub ↗

The first decision

Profile A or Profile B.

The difference is who activates the license. The rest of the core — offline, air-gap, editions, updates, notices, continuity — is the same in both.

Profile A

MCNexus activates the license.

The macOS and Windows app activates the license, downloads the product, installs, updates and rolls back on the workstation. The product embeds the SDK only to verify the certificate locally and read the license decision.

Applies to OFX plugins in post-production hosts. It avoids writing, signing and distributing a separate client.

User guide →

Profile B

The product activates its own license.

A product with its own installer links the SDK and activates, synchronizes and deactivates on its own, with no client app in the loop. The SDK detects windowed versus headless processes, for a server or a render farm.

Applies to native software outside OFX. Configuration is defined project by project.

Code

The lifecycle in three snippets.

Real API from the public NexKeyRuntime header, not pseudocode. The complete examples live in the SDK repository.

/* 1. Activate — Profile B, from the product itself. */
NexKeyRuntimeLicenseHandle *license = nexkeyruntime_license_create();
nexkeyruntime_license_set_product_data(license, PRODUCT_DATA);
nexkeyruntime_license_set_tenant_id(license, "tenant-id");
nexkeyruntime_license_set_variant(license, "download:entitlement");
nexkeyruntime_license_load_local(license);

PRODUCT_DATA is a blob issued by the backoffice for the tenant. It holds a public keyring and a base URL — no secret.

/* 2. Decide, on the render thread.
      No lock, no allocation, no syscall, no network. */
if (nexkeyruntime_license_render_decision(license)
        == NEXKEYRUNTIME_RENDER_ALLOW) {
    render(frame);
}

This is the one call that is safe inside a render callback. The license was resolved earlier, off the critical path.

/* 3. License state, off the critical path. */
NexKeyRuntimeLicenseSnapshot snapshot;
snapshot.struct_size = sizeof(snapshot);

if (nexkeyruntime_license_get_snapshot(license, &snapshot)
        == NEXKEYRUNTIME_OK) {
    printf("license status: %d\n", (int)snapshot.status);
}

nexkeyruntime_license_destroy(license);

The same structure reports the license edition. Enforcing what an edition allows is the integrator's job.

Platform

What is included.

Each item links to the section of the documentation that details it.

  • Node-locked activation: an Ed25519 certificate signed by a key scoped to a single tenant and bound to the machine fingerprint, with a seat limit per license and self-service deactivation. Two backends issue the license: OpenKey, the native one, and Cryptlex, for developers already using it. Distribution models →
  • Offline and air-gap: the certificate carries two independent deadlines — syncAfter, when the background thread starts trying to renew, and offlineValidUntil, the hard limit the SDK enforces. The issuer guarantees the offline window covers at least two full renewal attempts, so a failed sync is never what denies a license. Why an interruption is not a denial →
  • NexKeyRuntime: C/C++14 with a stable C ABI, macOS universal (arm64 and x86_64) and Windows x64. The repository publishes the full contract under Apache-2.0 — C header, JSON Schemas, documentation and examples. The API is at 0.x; result codes are append-only by policy. Client SDK →
  • MCNexus client: activates, installs, updates and rolls back on the workstation. Activating, deactivating, removing the local key and removing the plugin files are independent operations. User guide →
  • Key ownership and continuity: the keyring holds up to four keys, and a retired key stays in it and merely stops signing — which is why rotation does not invalidate what is installed. The recovery key is generated by the developer, and an upload containing its private half is refused. If the operator is no longer available →
  • Distribution and rollback: a download proxy with a short-lived signed token — the app never receives the real release URL. Platform-specific packages, version discovery, and reinstalling a previously published version. Security and distribution →
  • Editions and entitlements: beta, demo, trial and full — trial is time-limited, demo is not. The activation scope is unique per tenant, fingerprint and entitlement: the same machine cannot occupy two seats for the same right. Channels and editions →
  • Commerce and fulfillment: sales run through the developer's own Stripe account. Each sale records the order, the payment event and which version of the terms the customer accepted; fulfillment attempts are recorded per order, so a retried event does not issue a second license. Nexus Commerce flow →
  • In-product notices: severities critical, recommended and info, localized content and targeting by host, version range, platform and architecture. The content is text: HTML, arbitrary Markdown and script were left out by scope decision. Updates and notices ↗

First contact

How to start.

There is no signup and no self-service dashboard. Each integration is reviewed and configured project by project — self-service onboarding is on the roadmap.

  1. Product description

    Name, supported platforms, free or commercial distribution, and the licensing backend: OpenKey or Cryptlex.

  2. File preparation

    Per-platform packaging and release names following the pattern described in the documentation, so version discovery works.

  3. Publication

    The product is configured in Nexus and tested end to end. After that, new versions follow the same naming and packaging pattern.

Roadmap

What is not self-service yet.

The content of the NexKeyRuntime repository is Apache-2.0 and usable today. Access to the compiled binaries is arranged with each developer, under the binary license, and the API is at 0.x — result codes are never reused or renumbered, but the surface can still evolve.

The customer portal, tenant-owned storage, scheduled notices and self-service entry are items on the public roadmap, where the state of each is kept.
